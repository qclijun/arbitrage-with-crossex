## 2. B 与 A/A′ 的经济性对比（S_r\* 口径）

沿用 [rollover_watch.md](rollover_watch.md) v3 的公式，符号不变：

- `A = (L − E)·t_old·N + S·t_new·N − fee_A − settlement_A`
- `B_cash(S_r) = L·t_old·N + S_r·t_reopen·N − fee_B − settlement_B`；风险调整值另减主观折价R_B。
- 纯现金打平：`S_r_star_cash = (A − L·t_old·N + fee_B + settlement_B) / (t_reopen·N)`；风险调整线再加r_B。S/E/L均为裸APR；交易费按市场结算时钟，结算费两边显式扣除。A仍不代表完整净利润。

**关键差异**（相比 A/A′）：

| 项目 | A / A′ | B |
|---|---|---|
| 旧腿退出差 E | 立即实现，计入 A | **不实现**，按 L 计息到到期 |
| 新腿重开价差 | 现在锁定 S（exec 差） | 10-30 当天才知 S_r |
| Taker 费用 | 退出对 + 进入对 | 只有进入对（旧腿到期结算不收 taker） |
| 结算费 | 新腿持有期显式扣除 | 旧腿剩余期与新腿重开期分别显式扣除 |
| 资金费空档 | 无（新旧腿接续） | **有**，从旧腿结算到新腿首批成交 |
| 可执行性 | G已核验；对应规模须实时预检，实盘准入另核验 | 需本文获批 + 重开通道可用 |

**历史旧v2估算（费用口径已作废，不作当前决策）—2026-10-17 22:15**（`rollover_watch.md` 现有账本重算）：A ≈ $24.0，S_r\* ≈ 1.97%，S_cons（当日三次 S 最小值）2.37%，M = +0.40% → 倾向 B。但：

- 该 S_cons 只来自 **一天三次采样**，不代表 10-30 当天的分布；
- R_B（0.5% APR）是在没有重开通道实测数据时的假设；
- E（旧腿退出差）在观察账本中从 2.99% 漂到 4.17%，A 的数值随盘口变化而不稳定；B 不实现 E，因此不受此影响——这是 B 的真实稳定性优势。

**现行结论**：纯现金优势、主观风险折价与执行条件分别报告。旧v2样本不能作为v3收益/趋势基线；B未来重开价差未知，不预设哪一方占优。

## 3. B 的执行通道（实现事实）

### 3.1 步骤总览

1. **10-30 前**：无交易动作。只做监控与值守（见 §5）。
2. **10-30 00:00 UTC 结算**：旧腿按懒结算（lazy settlement）处理；REST 读取不需要手动触发。结算完成 ≠ 余额可提现 ≠ 保证金已释放（ROLLOVER-RESEARCH §6.3），三者须分别确认。
3. **结算后、重开前**：
   - 确认 196/198 持仓归零、无挂单、无未结算状态。`exitCalldatas` 会自动清理已成熟且无仓位的市场槽位（`borosApi.ts:667-691`），这一步通常随下一笔交易自动完成。
   - 确认永续 4 条腿仍在、净值中性（`risk_monitor` 的 `hedge.*` 指标）。
4. **重开**：一次 `POST /api/boros/pair/execute`，两腿同批提交（`intent: open`，方向：209 SHORT、213 LONG，本批各q ETH且q≤当前剩余R；已有新仓T作为基线，只核对本批增量）。
5. **重开后 1 小时 / 24 小时**：对账（§6）。

### 3.2 ⚠ 重开不是原子的（B 的核心风险）

| 事实 | 影响 |
|---|---|
| `pair/execute` 两腿同批提交，但 `submitBorosPair` 调 `placeMarketOrders` 时**未传 `timeInForce: 'fill-or-kill'`**（`orders.ts:374-381`），走默认 IOC（`borosApi.ts:731` TIF_IOC=1） | 两腿**可以部分成交** |
| `tryAggregate(requireSuccess=true)` 只保证「整批调用要么都成功、要么都回滚」 | IOC 下单成功≠按目标量成交；部分成交的 batch 仍算成功 |
| `submitBorosPair` 返回 `hedgedSize = min(fills)` 与 `unhedgedSize = |fills[0]−fills[1]|`（`orders.ts:394-396`） | 系统**会报告**未对冲数量，但不会自动补齐 |
| 补齐需要第二次请求（`onlyLeg`），而此时价格/深度已变 | 第二次补齐本身也有部分成交风险 |

**与 A 的对比**：A/A′ 用 `roll/execute`，四条腿全部 FOK、任一腿未全成交即整批 revert（G 已核验，见 `scripts/verify_roll_fok.ts`），**不存在部分成交**。B 的重开只有 IOC，这是结构性差异。

**缓解**（必须写进执行清单）：
- **首选**：两腿同批、足量、`slippageApr` 1.0% 提交；成交后立刻读 `unhedgedSize`，若有差额，用 `onlyLeg` 只补成交较少的那一腿，不重复开已足量的腿。
- **备选**（深度明显不足时）：以实时深度、最小交易量和已批准风险预算确定q≤R；逐批核对实际增量后更新R/T再报价，不固定试批数量，不承诺后续深度。IOC单腿不齐时的敞口须在§4已批准预算内。
- **任何部分成交都会留下净敞口**，必须在执行前设定「未对冲敞口容忍度」（见 §4 预算），且补齐必须在容忍时间内完成。
- 重开前必须确认旧腿已完全结算（持仓为 0），否则 `intent: open` 可能被 `flip-unacknowledged` 拦下（`pair.ts:1207-1213`）。

### 3.3 执行参数

以下为初始未滚场景的**历史参数示例，禁止原样提交**。已有A′成交后，实际size必须改为获批本批q≤新鲜R，已有新仓T不重复建立；旧示例的容忍与预算也不是当前批准值。

```json
POST /api/boros/pair/execute
{
  "address": "0x…",              // 必须是 config 中的 root
  "intent": "open",
  "opposingAcknowledged": true,   // 若新市场对已有持仓，需确认
  "legs": [
    { "marketId": 209, "direction": "short", "size": 3.9888313, "slippageApr": 0.01,
      "clientOrderId": "b209-<date>" },
    { "marketId": 213, "direction": "long",  "size": 3.9888313, "slippageApr": 0.01,
      "clientOrderId": "b213-<date>" }
  ]
}
```

- `slippageApr` 默认 0.25%，上限 10%（`pair.ts:55,60`）。B 的重开建议用 **1.0%**（与关闭旧仓用的 `CLOSE_SLIPPAGE_APR` 同量级）；若沿用 0.25% 默认值，按旧仓 10-30 的盘口先例（0.25% 下成交量为 0）很可能完全无法成交。
- `clientOrderId` 用于 10 分钟内的重放去重（`borosPair.ts:112`），**不是交易所级去重**。
- 单笔低于 $10 的订单会被 Boros 拒绝（`MIN_ORDER_VALUE_USD`）；按 $2400 计，试批不得低于约 0.005 ETH。

## 6. 验收与失败处置

### 6.1 重开成功标准

1. 209/213均从执行前基线T增加本批q，方向分别SHORT/LONG；全部剩余R重开完成后，逐平台新仓总量=T+R=原计划总量，不能在T之上再开原全量。
2. 本批`hedgedSize`=q，`unhedgedSize`=0；核对成交增量与receipt，不以总仓位代替本批成交量。
3. 保留的永续腿按当前数量逐venue与全部新旧Boros仓位核对（含非本计划市场）；不复用历史数量例子，也不只看净ETH为0。
4. HF ≥ 1.5，可用 ETH 不为 0，gas ≥ $2。
5. `risk_monitor` 的 `rollover.uncovered_funding_seconds` 回到 0。

### 6.2 失败分支

| 状态 | 处置 |
|---|---|
| 两腿都未成交 | 核对持仓未变；修正报价/滑点后重新模拟，**不机械重试同一 clientOrderId** |
| 一腿成交、一腿未成交 | 立即用 `onlyLeg` 补齐未成交腿；若补齐失败，在预算内平掉已成交腿，不留下净敞口 |
| 两腿都部分成交 | 用 `onlyLeg` 补齐较小的腿到与较大腿一致；差额在预算内处理 |
| 结算延迟 > 5 分钟 | 停止重开，按 `unknown` 处理；查 `tx-status-with-events` 与持仓，不猜测 |
| 重开后 HF < 1.5 | 停止后续操作，触发风险监控 WARNING，按应急方案处理 |
| API/终端失效 | 用已验证的备用查询渠道确认状态；状态不能核实时不扩仓、持续值守 |

> 关键原则（ROLLOVER-PLAN §6）：`unknown` 不推断成交，不盲目反向修复，不把「现有 Boros/永续重新配对」视为理所当然。
