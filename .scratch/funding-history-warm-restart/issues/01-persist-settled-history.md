# 01: 已结算历史落地，重启后先显示旧数据

**What to build:** 运行终端重启（`yarn stop` / `yarn start`）后，Funding 页面几秒内就显示重启前的历史数据，不再整页冷启动 UNKNOWN 等几分钟。每条腿的已结算记录、规则分段、读取与核验时间、Hyperliquid 回填进度都存进一个独立于账本的本地缓存；后台刷新器仍是唯一写入者。恢复出的数据保留原核验时间，标为“重启前数据，待核验”，只供查看：不参与排名，也不能通过开仓准入，直到本轮重新核验。中断的 Hyperliquid 长窗口回填从保存的页位置继续读，不从第一页重来。

**Blocked by:** None (can start immediately)

**Status:** ready-for-human（已实现，待签收）

背景：历史缓存现在只存在内存里，重启后从零开始；第一轮要整轮跑完才发布，长窗口还要多轮才能补齐。规划文档允许落盘，但要求“不能给旧数据换时间”。这里用独立缓存而不写进账本 SQLite，是为了不碰账本版本迁移，也不触发安装回退屏障。

## 存储方案（用户 2026-11-01 确认）

- **位置**：数据目录（跟随 `ARB_DATA_DIR`，默认 `data/`）下独立的 `funding-history.sqlite`，不放进账本 `deals.sqlite`。放进账本要走 ticket 20 的迁移流程、升级账本版本号、触发安装回退屏障；历史缓存可以随时删掉重建，不需要这些保护。
- **格式**：Node 自带的 `node:sqlite`（项目已在使用，不加依赖），开 WAL。每条腿的更新放在一个事务里，写一半中断不会留下半截数据。
- **权限**：文件为 `0600`，只限本人。SQLite 生成的 `-wal`/`-shm` 继承主文件权限。
- **唯一写入者**：后台刷新器。它和交易引擎在同一进程里，账本的 `EXCLUSIVE` 锁已经保证只有一个终端实例。
- **缓存格式版本**：用 `PRAGMA user_version`，和账本版本号互不相干；不符就删库重建。

大致表结构（实现时可调整，但要保留以下信息）：

| 表 | 一行代表 | 关键字段 |
| --- | --- | --- |
| `settlements` | 一次结算 | 交易所、合约、结算时间、费率（十进制字符串）、当时的结算周期、来源 API、原始页哈希；主键（交易所, 合约, 结算时间） |
| `reads` | 一次读取 | 截止点、覆盖区间、读取时间、核验时间、类型（补读/全量/复核）、页清单 |
| `legs` | 一条腿 | 规则分段、上市信息、上次复核时间、隔离原因、Hyperliquid 回填进度 |

## Answer

2026-11-01 实现，待用户签收。

- **落盘**：`data/funding-history.sqlite`，独立于账本（不改账本 schema、版本、备份），`node:sqlite` + WAL，文件及 `-wal`/`-shm` 为 `0600`。表为 `meta`、`legs`、`reads`、`settlements`（每次结算一行，证据字符串按读取去重成字典）。缓存格式版本用 `PRAGMA user_version`。
- **写入**：每轮发布后，后台刷新器只写有变化的部分（按值比对，重读值相同则不写），每条腿一个事务，腿之间让出事件循环。保存失败只记录原因，页面上显示提示，快照和页面读取不受影响。
- **恢复**：启动时先读缓存再开首轮。读出的每条读取都标 `restored`：保留原截止点和核验时间，`fresh` 恒为 false；排名原因为 `history-restored`，服务端开仓复核返回 `history-restored`。页面显示“重启前数据，待核验”及保存时间。同一截止点上，本进程的读取优先于恢复的读取；恢复的腿与从未读过的腿一起最先重读。Hyperliquid 回填任务（截止点、段、页游标、已读记录）原样续读；续读得到的长窗口仍标 `restored`，直到被本进程的新任务替换。
- **丢弃**：版本不符、不是数据库、任何字段读不回、缺快照元数据、`retained` 有缺口等，整个文件删除重建，页面给出原因。IO 或权限错误、或加载中途关闭，不删文件，按不可用处理。
- **测试**：按用户选定的测试接缝，只在存储层测试（`tests/server/funding-history-store.test.ts`，11 项）：完整往返、多次保存后与最新状态一致、各类损坏整体丢弃后可重建、权限 `0600`。排名规则、刷新器续读和页面文案没有新增测试，靠既有套件防回归。
- **规模实测**（合成数据，2,600 条腿、约 420 万条结算）：首次全量保存 8.5 秒，事件循环单次最长阻塞 52 毫秒；常规一轮（约 100 条腿）0.39 秒；启动加载 7.6 秒，单次最长阻塞约 0.5 秒（推测为 GC）；文件 357 MB。
- **已知限制**：
  - 一次保存按腿提交，不是整轮原子。中途退出时，文件里会混有两轮的腿；每条腿自身一致，且恢复的数据只供查看。
  - 终端没有优雅停机钩子（`yarn stop` 直接结束进程），最后一轮可能只保存了一部分。
- **验证**：`GATE_PROXY= yarn verify` 和 `yarn --cwd web build` 通过。需要清空 `GATE_PROXY`：`.env` 里的代理会让 3 个官方源测试文件的请求走代理，被 nock 拦截；未改动的基线上同样失败。线上服务未重启。
