# Positions 默认统计起点与 Boros 手续费完整性

## 已验证的问题

默认统计起点取自 Gate 支持资产的首次永续开仓时间。Boros 开仓可以发生在永续开仓之前，导致其真实成交手续费被默认窗口排除，进而影响费用明细和收益。

合成回归案例：Boros 两腿在 T 时刻成交，永续首次开仓在 T+25 秒。两腿各支付 0.0004 ETH，合计 0.0008 ETH。默认窗口须覆盖 T 时刻；这些示例不对应个人账户、真实交易时间或实付金额。

## 已确认的修复范围

- 修复 Positions 的默认统计起点，覆盖成交链能够确认的当前持仓周期，完整计入该周期费用。
- 不用固定向前减几十秒的方式补偿，不直接纳入全部 Boros 历史，不新增策略轮次管理系统。
- 现有四腿配对根据当前持仓、交易所、到期日及数量推导，没有明确的策略轮次 ID；配对本身不能证明历史费用归属。
- 根据成交历史确认当前持仓周期，避免把同市场已结束周期的费用归入当前周期；无法确认时明确表示统计不完整。
- 兼容并自动修正旧的错误默认起点，修正结果按 Gate 账户与 Boros 钱包组合隔离。
- 用户显式设置的总起点及分腿起点 legSince 继续生效，按期间严格统计，不因默认起点修正而扩大用户选定窗口。
- 补计费用后同步更新 Boros Trade Fees 及依赖费用的收益、预计到期利润等数字；说明变化来自补计历史费用。
- 本次不修改 Trades 页面，不新增生命周期费用展示，不改变交易执行、订单或持仓。

## 交付顺序

1. 工单 01：修复默认起点与漏计费用，包含旧记录兼容、账户组合隔离及收益联动。
2. 工单 02：依赖工单 01，完成历史不完整、无法确认归属及手动日期边界的展示与验证。

## 验证边界

使用脱敏 fixture、离线服务端/API 和必要的 UI 测试验证。运行相关离线测试及类型检查。不得用真实交易测试作为验收，不操作真实订单，不改变账户仓位。旧记录只在所属账户范围内兼容修正，不要求用户清空历史或手动修改持久化文件。

可证明的持仓周期不等于明确的策略轮次身份。若历史不足以判定归属，不能将缺失费用当作零，也不能声称当前策略完整成本已确认。
