# 历史证据与机会资格契约

来源：[工单01](issues/01-history-and-eligibility.md)，2026-10-27用户逐项确认Q1—Q4。
本文件细化已确认规则，供后续任务实现；整体[规格](spec.md)仍为draft。

## 窗口与共同截止点

- 每轮快照取最近已结束的UTC整点为`cutoff`，窗口天数为7/30/90/180/365，默认30。
- `start = cutoff - days × 24小时`，只计入`(start, cutoff]`内已实际结算的费率。恰在起点的事件不计，恰在截止点的事件须有已结算证据才计入。
- 同一快照所有方向、场所和窗口共用cutoff；不得为较慢场所后退全市场截止点，或拼接不同截止点的两腿结果。
- 每个方向固定short/long两腿，各窗口分别计算`Σshort − Σlong`，简单年化为该差值乘`365 / days`。费率及累计值采用十进制字符串，合法零值和负值均保留。
- 按实际结算时刻和规则验证覆盖，不强求两腿有相同周期/条数；不把当前预测率或当前bulk feed当成已结算历史。

## 逐腿逐窗口证明

必须证明窗口内所有预期结算已覆盖，且来源/分页读取完成。最早最晚时间和返回条数不能单独证明完整。

- 周期发生8小时→4小时等变化时，按生效时间分段验证，包括变化边界；无法证明规则时为UNKNOWN。
- 同venue、同合约、同结算事件的经济记录完全相同则去重，不因重复页重复计息；费率或周期等实质字段冲突时为UNKNOWN，保留冲突证据，不任意选一条。
- 少一期、分页未完成、无法核实的周期或来源失败，均不补零。明确记录缺失区间/事件、失败原因及来源；来源根本未知时也须明确说明，不伪造精确缺口。
- 新币上市前的区间不是零费率。上市10天不满足30天，只有完整的7天窗口可合格；90/180/365天不足不拖累完整短窗口。
- 资格逐组合判断：某场所失败只影响涉及该场所的组合，其他双腿完整组合继续参与。两种交易方向共享覆盖证据，但分别计算资金费差。

## 来源与状态契约

以下为字段语义，具体TypeScript接口与持久化结构由08实现。

| 范围 | 必需证据 |
|---|---|
| 快照/方向 | snapshotId、cutoff、start/end、days、underlying、short/long venue及精确合约标识 |
| 每腿 | 历史来源/API及来源版本、observedAt、verifiedAt、已结算事件、结算周期分段与依据、分页完成证明、上市/历史起点依据 |
| 每窗口覆盖 | complete/partial/unknown/unsupported、缺失区间/事件或无法定位的说明、冲突及原因 |
| 刷新 | 最近尝试及结果、最近成功核验时间、错误/限流/预算耗尽原因、fresh/stale |
| 结果 | 双腿累计/年化、固定方向净差/年化、排名资格、历史准入及独立执行阻止原因 |

- `complete`：已证明覆盖整个窗口；`partial`：有可用记录但存在已知缺口；`unknown`：证据不足，无法判定完整性；`unsupported`：经核查无可用生产历史源。尚未研究不能声称unsupported。
- 非complete窗口对外排名值为UNKNOWN，不以部分累计值或零值填入可比较年化；已取得的原始证据仍可供解释。显示UNKNOWN时同时展示覆盖状态与原因。
- fresh/stale与覆盖独立：完整旧缓存也可能stale；新抓取的partial也可能fresh。只有两腿所选窗口都complete且fresh，才有历史排名资格及历史准入。
- `observedAt`表示源读取时刻，`verifiedAt`表示完成覆盖核验时刻。旧记录重新读取后可重新验证同一截止点；仅更新时钟或收到HTTP成功不算核验成功。
- 覆盖充分不代表所有执行条件充分。账户费率未知不阻止历史资金费差排名，但单独阻止下单；白名单、单位、成本、余额等门槛仍由02/03及服务端执行链校验。

## 后台采集、缓存与预算

- 后台独立采集，15分钟内刷新一次；页面请求只读取缓存与状态，不触发同步全市场历史抓取。冷启动无缓存时显示UNKNOWN/加载状态。
- 当前时间距相关证据最近成功核验时间超过15分钟，或快照cutoff落后于当前最近已结束UTC整点时，为stale；跨整点即使未满15分钟也须重新核验新窗口。
- 刷新失败保留最近可用快照及原核验时间，并显示失败原因；不能清空其他场所的成功结果或把失败重试伪装成新鲜数据。旧快照仍满足时效与cutoff条件时可沿用，条件失效后仅供观察，暂停排名与下单。
- 刷新尝试与成功覆盖证据分开记录；未完成的新截止点不能覆盖旧完整证据并伪装complete。发布的可比较结果必须绑定共同cutoff。
- 每轮须有请求数、并发、超时及重试上限；遵守场所限流，预算耗尽或限流时停止对应抓取，明确原因，不无限重试、不由页面补抓。具体数值由07查证场所约束、09确定并离线验证，不能承诺15分钟内必定补齐全市场全部历史。
- stale、partial、来源失败及不支持项均留在观察集合并解释原因。服务端下单预检必须重查历史准入；不能仅凭页面按钮状态或旧snapshotId放行。

## 决策验收例子

| 输入 | 所选窗口与预期 |
|---|---|
| 新币上市10天，已证明7天完整 | 30天UNKNOWN、不排名/下单；切7天可取得历史资格，长窗口不足不拖累 |
| HL窗口内少一小时结算 | 涉及HL的该窗口partial/UNKNOWN，两方向均无资格，不补零 |
| Binance期间8小时改4小时 | 有规则分段及全部事件则complete；仅条数正确或缺变化依据不合格 |
| 重复页/冲突 | 完全相同事件只计一次；同一期经济字段冲突为UNKNOWN |
| A场所失败，B和C完整 | A相关组合受影响；B/C两方向仍分别比较，不回退全市场cutoff |
| 历史完整新鲜，账户费率未知 | 可排名，但费用未知独立阻止下单，由03定义预检细节 |
| 覆盖完整但核验超过15分钟 | complete + stale，仅观察；失败重试不能延长核验时间 |
| 缓存仅1分钟，但已跨UTC整点 | 原cutoff落后，stale；不得拿旧窗口进入当前排名 |
| 起点/截止点各有一条结算、其中有零/负率 | 起点排除，截止点已结算才计入；保留合法零/负率 |
| 冷启动/限流/预算耗尽 | 明确UNKNOWN及原因；不阻塞页面，不伪造覆盖或新鲜度 |

以上将成为08/09的离线验收输入，不代表当前产品已经通过这些用例。
