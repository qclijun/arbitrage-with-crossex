# 历史证据与机会资格契约

来源：[工单01](issues/01-history-and-eligibility.md)，2026-10-27用户逐项确认Q1—Q4。
本文件细化已确认规则，供后续任务实现；整体[规格](spec.md)已定稿，08纯计算/证据模型已完成验收，生产采集与接线仍按后续任务交付。

2026-10-31用户变更：**不需要严格的历史规则证据，优先从已结算资金费率数据推算周期**。以下按此约定执行；旧工单中要求独立历史规则证明的条款由本次变更替代。

## 窗口与共同截止点

- 每轮快照取最近已结束的UTC整点为`cutoff`，窗口天数为7/30/90/180/365，默认30。
- `start = cutoff - days × 24小时`，只计入`(start, cutoff]`内已实际结算的费率。恰在起点的事件不计，恰在截止点的事件须有已结算证据才计入。
- 同一快照所有方向、场所和窗口共用cutoff；不得为较慢场所后退全市场截止点，或拼接不同截止点的两腿结果。
- 每个方向固定short/long两腿，各窗口分别计算`Σshort − Σlong`，简单年化为该差值乘`365 / days`。费率及累计值采用十进制字符串，合法零值和负值均保留。
- 按实际结算时刻和规则验证覆盖，不强求两腿有相同周期/条数；不把当前预测率或当前bulk feed当成已结算历史。

## 逐腿逐窗口覆盖检查

按推算或已提供的周期生成预期结算，逐期检查窗口覆盖，并要求来源/分页读取完成。`complete`表示通过这套检查，不宣称获得独立历史文档证明。

- 生产优先从同合约的已结算时间戳推算周期。连续三个相同间隔确认一个分段，支持1/2/3/4/6/8/12/24小时；持续8小时→4小时等变化按时间分段。单次较大间隔沿用周围周期检查缺期，短异常尾段不能直接升级为新周期。
- 保存并展示`cadence.basis=inferred`、周期集合和样本数；数据推算通过覆盖与新鲜度检查后可参与排名和历史准入。推算不足时可使用已有规则；两者都不可用时为UNKNOWN，显示样本不足原因。
- 推算模式允许把整点后不超过999毫秒的处理时间归到该整点，原始时间和推算映射依据同时保留；更大的不规则时间偏移不据此归一化。
- 只有在上市信息缺失时，允许用首条记录所在推算周期的起点估计历史存在边界，并明确标为推算；已有精确上市时间继续保留。系统性漏记可能与持续周期变更难以区分，这是数据推算的限制，不能把结果标为文档已核验。
- 同venue、同合约、同结算事件的经济记录完全相同则去重，不因重复页重复计息；费率或独立周期字段冲突时为UNKNOWN，保留冲突证据。由算法推算的周期可随新数据重算，不把估计更新当成费率修订。
- 少一期、分页未完成、无法核实的周期或来源失败，均不补零。明确记录缺失区间/事件、失败原因及来源；来源根本未知时也须明确说明，不伪造精确缺口。
- 新币上市前的区间不是零费率。上市10天不满足30天，只有完整的7天窗口可合格；90/180/365天不足不拖累完整短窗口。
- 资格逐组合判断：某场所失败只影响涉及该场所的组合，其他双腿完整组合继续参与。两种交易方向共享覆盖证据，但分别计算资金费差。

## 来源与状态契约

以下为字段语义，具体TypeScript接口与持久化结构由08实现。

| 范围 | 必需证据 |
|---|---|
| 快照/方向 | snapshotId、cutoff、start/end、days、underlying、short/long venue及精确合约标识 |
| 每腿 | 历史来源/API及来源版本、observedAt、verifiedAt、已结算事件、周期分段、cadence推算来源/周期/样本数、分页完成记录、上市/历史起点及其推算标记 |
| 每窗口覆盖 | complete/partial/unknown/unsupported、缺失区间/事件或无法定位的说明、冲突及原因 |
| 刷新 | 最近尝试及结果、最近成功核验时间、错误/限流/预算耗尽原因、fresh/stale |
| 结果 | 双腿累计/年化、固定方向净差/年化、排名资格、历史准入及独立执行阻止原因 |

- `complete`：来源及分页有效，按所用周期检查没有缺期或冲突；周期可为推算并须显示来源。`partial`：有可用记录但存在已知缺口；`unknown`：样本/来源不足或有冲突；`unsupported`：经核查无可用生产历史源。尚未研究不能声称unsupported。
- 非complete窗口对外排名值为UNKNOWN，不以部分累计值或零值填入可比较年化；已取得的原始证据仍可供解释。显示UNKNOWN时同时展示覆盖状态与原因。
- fresh/stale与覆盖独立：完整旧缓存也可能stale；新抓取的partial也可能fresh。只有两腿所选窗口都complete且fresh，才有历史排名资格及历史准入。
- `observedAt`表示源读取时刻，`verifiedAt`表示完成覆盖核验时刻。旧记录重新读取后可重新验证同一截止点；仅更新时钟或收到HTTP成功不算核验成功。
- 覆盖充分不代表所有执行条件充分。账户费率未知不阻止历史资金费差排名，但单独阻止下单；白名单、单位、成本、余额等门槛仍由02/03及服务端执行链校验。

## 后台采集、缓存与预算

- 后台独立采集，15分钟内刷新一次；页面请求只读取缓存与状态，不触发同步全市场历史抓取。冷启动无缓存时显示UNKNOWN/加载状态。
- 当前时间距相关证据最近成功核验时间超过15分钟，或快照cutoff落后于当前最近已结束UTC整点时，为stale；跨整点即使未满15分钟也须重新核验新窗口。
- 刷新失败保留最近可用快照及原核验时间，并显示失败原因；不能清空其他场所的成功结果或把失败重试伪装成新鲜数据。旧快照仍满足时效与cutoff条件时可沿用，条件失效后仅供观察，暂停排名与下单。
- 刷新尝试与成功覆盖证据分开记录；未完成的新截止点不能覆盖旧完整证据并伪装complete。发布的可比较结果必须绑定共同cutoff。
- 每轮须有请求数、并发、超时及重试上限；遵守场所限流，预算耗尽或限流时停止对应抓取，明确原因，不无限重试、不由页面补抓。具体数值由07查证场所约束、09确定并离线验证，不能承诺15分钟内必定补齐全市场全部历史。
- stale、partial、来源失败及不支持项均留在观察集合并解释原因。服务端下单预检必须重查历史准入；不能仅凭页面按钮状态或旧snapshotId放行。

## 决策验收例子

| 输入 | 所选窗口与预期 |
|---|---|
| 新币上市10天，已证明7天完整 | 30天UNKNOWN、不排名/下单；切7天可取得历史资格，长窗口不足不拖累 |
| HL窗口内少一小时结算 | 涉及HL的该窗口partial/UNKNOWN，两方向均无资格，不补零 |
| Binance期间8小时改4小时 | 数据中持续周期变化形成分段，逐期检查通过则complete并标记inferred；孤立缺期或短异常段仍不合格 |
| 重复页/冲突 | 完全相同事件只计一次；同一期经济字段冲突为UNKNOWN |
| A场所失败，B和C完整 | A相关组合受影响；B/C两方向仍分别比较，不回退全市场cutoff |
| 历史完整新鲜，账户费率未知 | 可排名，但费用未知独立阻止下单，由03定义预检细节 |
| 覆盖完整但核验超过15分钟 | complete + stale，仅观察；失败重试不能延长核验时间 |
| 缓存仅1分钟，但已跨UTC整点 | 原cutoff落后，stale；不得拿旧窗口进入当前排名 |
| 起点/截止点各有一条结算、其中有零/负率 | 起点排除，截止点已结算才计入；保留合法零/负率 |
| 冷启动/限流/预算耗尽 | 明确UNKNOWN及原因；不阻塞页面，不伪造覆盖或新鲜度 |

以上将成为08/09的离线验收输入，不代表当前产品已经通过这些用例。

## 修订 2026-10-31：周期双重证明

原契约禁止仅凭相邻结算间隔推断历史周期。用户于2026-10-31批准修订：周期段仅在同时满足下列两条时视为已证明：(1) 官方历史页读到的该区间结算记录完全规则——相邻间隔恰为`everyHours`，全部落在该周期的UTC整点网格上，无任何异常记录；(2) 该周期等于场所当前官方周期（Binance fundingInfo，缺省按文档8小时；OKX fundingTime−prevFundingTime；Bybit fundingIntervalHour），且当前周期读数新鲜（15分钟内）。出现任何不规则间隔、周期变化边界、缺失记录或与当前周期不一致，该区间保持UNKNOWN（schedule-unverified），不拟合、不补零、不取整。较短的、完全落在已证明区间内的窗口仍可complete。原条文保留作历史，本节为现行规则。

实现要点：每腿只证明以最新结算结尾的一段连续规则记录，且至少两条；最新一期尚未发布（最新记录加一个周期不晚于截止点）时整腿UNKNOWN，直到下一轮读到。证明被拒时该腿照常发布核验时间与原因（`schedule:<原因>`），但不发布任何事件，避免未经规则担保的周期标记进入后续合并。缺失记录不再产生partial：跨越缺口的窗口为UNKNOWN，缺口之后的较短窗口仍可complete。上表“Binance期间8小时改4小时”一例相应改为：仅完全落在变化后4小时连续段内的窗口complete，跨越变化边界的较长窗口UNKNOWN。Binance/Aster当前周期缺省8小时时，规则证据文本不区分“文档缺省”与fundingInfo明示（当前周期报价不携带来源标记）；缺省若错误只会导致周期不一致而UNKNOWN，不会产生错误的complete。

Binance毫秒抖动（用户于2026-10-31另行批准）：只读实测Binance `/fapi/v1/fundingRate` BTCUSDT/ETHUSDT 共500行中249行的fundingTime为整点加0—15毫秒（如1779033600009）；OKX与Bybit记录全部恰在整点（95天/66天内间隔均为8小时）。仅对BINANCE，原始fundingTime落在[整点, 整点+1000毫秒)时映射为该整点结算，事件保留rawTime与映射证据；超出1000毫秒仍按原始时间处理（不在网格上，中断连续段），整点之前的时间不向前映射。分页查询的上界相应延伸999毫秒，以读到截止点那一期带抖动的记录。Aster与Hyperliquid不变：Aster不映射，Hyperliquid仍须独立结算小时证明。
